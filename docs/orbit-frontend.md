# Orbit frontend on Windows

Choose **Interface → Orbit Store** in the native toolbar. **Classic Windows** remains the initial default. Discover, Browse, Library, Downloads and Settings share the graphical shell in all four Orbit layouts. Settings contains eleven borderless category tiles, including Appearance, Language and Metadata (IGDB media); Arguments remain under KytyPS5. The WebView stays visible and the header, footer and controller loop remain in place. Escape, right-click and controller B/Circle return from a detail to Settings home, then to the actual previous page. Dropdowns and confirmation dialogs consume Back first. F11 changes fullscreen without closing Settings. These routes keep one `MainViewModel`, settings owner, download manager and installation journal alive. Changing the interface never calls their cancellation/disposal methods. Native padding/status are hidden in fullscreen; the toolbar slides down at the top edge or with F6 and hides after the pointer leaves, except while using its keyboard controls or interface menu. Classic/failure fallback restores the normal window. Use F11 to exit fullscreen. Normal bounds and maximized state are restored and saved.

Use **arrow keys or WASD** for directional navigation, **Enter** to activate and **Escape** to go back. WASD passes through in editable controls and ignores modifier shortcuts. Navigation uses the original controller/widgets with immediate scrolling. **Appearance (F2)** in the native toolbar, or F2 inside Orbit, opens the Appearance category in the same Settings page. It closes other Orbit release dialogs first; interface confirmation, motion, accent, background preferences and language remain upstream-owned. The toolbar wraps on narrow windows.

To download, open the game, use **View releases** where shown, choose its source/version, then **Download**. The release dialog offers the existing Direct, Browser-assisted, External browser and Import completed file functions according to the native provider policy. Direct starts the existing HTTP manager; Browser-assisted opens the existing isolated provider window. Unknown providers offer external browser/import. The real native queue, completed-download extraction/installation, installed library actions and installation history are managed in Orbit. Native pickers, passcode/installation dialogs, restart/discard prompts, exact-path deletion confirmation and cleanup confirmation remain unchanged. Graphical Settings reads and writes an explicit allowlist through the in-process Windows adapter. Model setters retain persistence and validation; native handlers retain picker, confirmation and updater ownership. Classic keeps its WPF settings controls and shares that model/store. The category hub, artwork and control mapping are documented in [Settings UI](settings-redesign.md).

## My Library cover grid

The Windows adapter renders My Library as a responsive 2:3 cover grid in the existing Orbit library route. Search, title/compatibility sorting and compatibility filtering are local presentation state. The header shows the installed count and current emulator build once. Library tools and installation activity remain in a disclosure below the collection.

Click a poster, press Enter, or use controller A/Cross to invoke the existing Play action. Arrows/WASD navigate the rendered rows; Tab reaches More, and controller X/Square opens More for the focused game. More contains compatibility, launch logs, folder/reinspection/install actions where available, and the existing two-second deletion hold with native ownership/token checks. Installation Details reads the existing journal into a web dialog so controller Back can close it. It accepts only a retained library ID, never a caller-supplied file path.

The compatibility view keeps four records separate: Official KytyPS5, Official SharpEmu, Local KytyPS5 and Local SharpEmu. On startup the app refreshes KytyPS5's compatibility feed and SharpEmu's published `games-index.json`; SharpEmu title aliases are indexed by PPSA ID, and failed or unavailable feeds remain unavailable rather than being treated as untested. The game About section displays all four statuses. Each library poster has a four-quarter marker in the same order, with dark status-colour fills for official results and light fills for local results. The compatibility editor saves both local statuses together and records each installed emulator version when available. It does not submit a community report.

Badges follow SharpEmu's five status colours: Nothing (red), Boots (orange), Menus (yellow), Ingame (blue) and Playable (green). KytyPS5's existing labels stay intact and use the corresponding visual colour family. Not tested and unavailable use neutral grey.

Status UI review: the four poster segments expose their source and status names in the accessible label and tooltip, while the About rows show visible status text (UI-A11Y-005, WCAG 2.2 AA). Local badges pair pale fills with darker status text; official badges use dark fills with bright text (UI-A11Y-004, WCAG 2.2 AA). The local-status editor uses labelled native selects and a single save action (UI-A11Y-008).

Pointer hover opens a preview after 200 ms; keyboard/controller focus opens it immediately. One viewport-bounded text panel joins the poster edge, flips to the available side, and does not duplicate the artwork or change grid geometry. Reduced motion disables its entrance animation. More keeps management separate from the poster's launch surface, and closing details restores focus to the invoking game.

Escape, right-click and controller B/Circle use Back: dismiss a modal/menu, dismiss the current preview, then return through actually visited pages. With no previous page, Back is a no-op. F11 remains the fullscreen toggle. The existing controller poller acts only while its document is visible and focused. Startup, disconnection, blur and visibility changes require all buttons and sticks to return to neutral before another controller command can run. No OS input hooks or second poller are installed.

### Focused validation

`dotnet run --project PS5CatalogBrowser.BrowserTests -c Release -- --cover-grid` exercises the actual WebView2 adapter with synthetic installed games and in-process geometric artwork. It covers compatibility source/contrast, responsive columns, hover/focus geometry, navigation history, details, exact command routing, ineligible Play, focus loss and held-button/stick return, reduced motion, filtering, and unchanged saved records. `--library-cards` retains the existing compatibility persistence/rollback, log and deletion transaction checks. `--compatibility` checks the existing Browse presentation and four interfaces; `--game-return` checks native process exit to Library.

Set `PS5_ORBIT_EVIDENCE` to capture rendered PNGs at 1920×1080, 1280×720, 720×800 and 390×760, plus hover/focus, More, details and an edge preview. Local evidence is kept under `UI/local-evidence/cover-grid` (ignored). Test gamepads replace `navigator.getGamepads` only in the temporary test profile. Physical controller/Windows driver acceptance remains a manual check.

UI standards review: native labelled controls, visible focus, source/status text beyond colour, measured chip contrast ≥4.5:1, 44px secondary targets, reduced motion, portal bounds and unchanged deletion safeguards are covered by the focused checks. These checks do not constitute a screen-reader or physical controller audit.

## Source and build

The original browser frontend is from [Orbit Store v1.3.5](https://github.com/saawant12/orbit-store-ps5/releases/tag/v1.3.5), source commit `8043189a7d319be3ffdf828e08bf5a0f105a30fd`. `UI/provenance.json` records the verified outer release digest and inner source digest. The guide repository's commit differs from the source commit recorded by `SOURCES.json` in that bundle.

`UI/orbit-upstream` contains 101 byte-identical upstream frontend/build/licence files. `UI/upstream-files.json` records each SHA-256; `.gitattributes` prevents line-ending conversion. No original source file is edited. The original Store, Crossbar, Cinema, Panorama, Appearance, confirmation, language, keyboard, artwork and typography implementations remain upstream-owned.

Install Node.js 22 and .NET 10, then run from the repository root:

```powershell
powershell -NoProfile -File UI/build-frontend.ps1 -Restore
dotnet build PS5CatalogBrowser.slnx -c Debug
dotnet build PS5CatalogBrowser.slnx -c Release
```

The script verifies upstream hashes, restores the lockfile with `npm ci --ignore-scripts`, typechecks the original frontend and adapter, and runs Vite using the external Windows configuration. It deliberately does not invoke upstream npm build scripts that generate PS5 backend/catalogue assets. MSBuild rebuilds the frontend when its inputs change and copies the verified output into `OrbitFrontend` for application/test output and publishing. Generated assets, downloaded archives and `node_modules` are ignored. Native initialization checks every packaged asset's digest, rejects linked paths, and serves only those verified in-memory members. The manifest is a packaging/integrity check, not a signature against an attacker who can replace the executable and bundle.

`UI/windows-adapter/vite.config.mjs` substitutes console-only panels with Windows management components. Appearance and Language remain original. Exact build anchors mount the independent Appearance shortcut and Windows release dialog, route native page notifications, use immediate controller scrolling, label Store/Cinema options **View releases**, connect desktop download actions to the release dialog, label browse actions **View game**, and show **Size unknown** where needed. Metadata-only options cannot download. Changed anchors fail the build. Original styles/layout files remain unchanged; Windows management panels have separate adapter CSS.

Upstream GPL and applicable React, scheduler, Vite and font notices are retained in `UI/orbit-upstream/LICENSE`, `THIRD-PARTY-NOTICES.md` and `licenses/`. The full upstream notices describe other components in the complete PS5 release; those native components are not bundled here. Game names/artwork remain external and are not licensed by Orbit. Before distributing this combined application, review GPL source/distribution obligations and third-party asset rights. This milestone is for private local use.

## Adapter contract 2 (web-message schema 1)

`OrbitFrontendCatalog.Create` projects already-normalized C# catalogue entries. It never decrypts feeds, opens keys, handles providers or creates jobs. HTTP JSON, OptiStore, Homebrew, local Orbit and live Orbit continue through their existing Core readers. Unsupported platforms and ambiguous IDs are omitted with diagnostic issues, and remain inspectable in Classic Windows.

| Field | Windows meaning |
|---|---|
| `gameId` | SHA-256 of explicit source ID, entry ID and platform, with a presentation prefix. Titles, artwork, file sizes and filenames never form identity. |
| `id` | Source/entry/platform plus exact artifact ID. Metadata-only entries have an explicit null artifact identity and a separate presentation release. |
| Native `WindowsIdentity` | Exact source ID, entry ID, artifact ID, platform, title ID, version, region, provider and format remain in C#. They are resolved from the opaque release ID at action time and rechecked against current enabled entries. The redundant identity object is no longer exported in catalogue JSON. Alternatives never become multipart files. |
| `windowsAvailable` | The option has an artifact that can be resolved for existing native operations. It grants no transfer capability. |
| `sourceId`, `provider` | Source-scoped provider grouping and catalogue/provider label for Orbit's source filter. Original provider identity remains in `windowsIdentity`. |
| Size/artwork | Unknown size is `-1`; image URLs must pass existing HTTPS/loopback policy. Original artwork fallbacks/layout metadata remain available. |
| Availability | `platform: desktop`; no console verification, direct or browser download capability is granted. |

Read API paths under `/api/v1`: `system`, `sources`, `catalog`, `favorites`, `browser`, `debrid`, `storage`, `downloads`, `library`, `library/storage`, `windows/status`, `windows/state`. `downloads` projects real native jobs for the original shell queue summary; `windows/state` projects explicit queue, installed-library and installation DTOs with currently available actions and native progress/status. Console storage, browser sessions, debrid and original console-library hooks remain compatibility envelopes; the displayed Windows panels use native state. No raw settings/job object, source file, decoding key, provider capability URL, archive password or emulator path is exported. React renders metadata as text.

`POST favorites` accepts exactly `{gameId, favorite}` and uses the native settings writer with rollback. `POST windows/release` accepts exactly `{id}` and returns current native release actions. `POST windows/action` accepts exactly `{action, id}`: a fixed allowlist plus an opaque current release ID, retained native job/library/installation ID, or empty ID for a global action. Requests are bounded, reject duplicate/extra fields and recheck the enabled source/exact identity/action eligibility. A `202` acknowledgement precedes dispatcher execution so native dialogs cannot block the resource response. Eligibility is rechecked before dispatch; existing handlers retain admission, persistence, confirmations and ownership. Unknown/stale identities cannot invoke an operation. React never supplies filesystem paths, URLs, shell arguments or package credentials and keeps no parallel download/library/settings store. Appearance/language retain their original separate profile preferences.

Orbit opens before source refreshes finish, so one slow/offline feed does not delay the interface. Projection validates artwork once per entry and hashes provider groups once per source/provider. Missing artwork avoids exception-based validation. Encoded catalogue JSON is cached until the native catalogue/source snapshot changes, omits null optional fields and redundant native identity records, and is reused across frontend polls/reloads. There is no second catalogue store or persisted plaintext cache. See the validation notes for measured costs and remaining first-load/network work.

## KytyPS5 compatibility

Startup independently fetches the [compatibility page's JSON index](https://kytyps5.github.io/data/compat-index.json), with a 15-second deadline, 2 MiB limit and no redirects. Only exact PPSA IDs (optionally hyphenated) match; names and filenames are never used. The site's `overall` status is the best reported result across operating systems, not a Windows-specific or local launch test. The in-memory result adds `windowsCompatibility` to the catalogue projection and revision so polling updates existing cards. Unmatched IDs show **Not tested** after a successful fetch; absent/failed initial data shows **Status unavailable**. Community feed data is not persisted; manual overrides are saved separately in settings.

Store, Panorama and Cinema thumbnails and Crossbar rows show status badges; Browse has a **Compatibility** dropdown that combines with existing filters and resets with **Reset filters**. Upstream files remain unmodified; changes use the Windows build adapter.

Startup also fetches individual `/data/compat/{PPSA}.json` reports for verified library title IDs (four concurrent requests, a shared 15-second deadline, and the same per-response size/redirect limits). Each website report retains its own status, tested version, OS and date; an overall status is never assigned another report's tested version. These optional in-memory details cannot overwrite local results, and unavailable details leave the overall index usable.

UI review: status text accompanies colour, Store card accessible names include compatibility, and the dropdown retains Orbit's labelled combobox and keyboard controls. Badges use the site's status palette, a dark backing for artwork contrast, and lighter text for Not tested. Synthetic WebView2 checks cover filtering/reset and badges in all four layouts without horizontal page overflow. These reports do not establish gameplay compatibility on this machine.

## Library cards

Windows library cards show a left-hand poster from recorded artwork or an unambiguous catalogue/title-ID match, with the standard Orbit fallback when unavailable. A source toggle selects website or local compatibility results; the compatibility filter and colored poster dot follow the selected source. Tests recorded against an older dated KytyPS5 build receive a dark red dot border. Play invokes the existing launch attempt handler; it does not promise compatibility. Open folder, Reinspect and Installation details are secondary actions in a keyboard-accessible ellipsis disclosure.

Delete requires a continuous two-second pointer, Enter or Space hold. Releasing early, moving off the button, losing focus, scrolling or cancelling the pointer resets the dial. `POST windows/delete/prepare` accepts only the retained item ID and captures the existing deletion plan. It returns an opaque one-use token and the exact recorded paths shown beside the hold control. `POST windows/delete/confirm` accepts only ID/token after at least two seconds and within 30 seconds; dispatch carries the captured plan into the existing native deletion transaction, which rechecks paths, identity, ownership and protected roots before recycling. Classic retains its existing confirmation dialog. No automatic or restart deletion is introduced.

Compatibility editing accepts only the five known report statuses or a reset to community status through `POST windows/compatibility` (`id`, `status`). Overrides are saved locally in settings, shared with Browse by verified PPSA ID where available, and otherwise scoped to the library record. Save failure rolls back the edit. Local overrides are labelled as local and never submitted to the community site.

The configured executable's version is read at startup and whenever its path changes, without executing it. A unique embedded `KytyPS5-YYYY-MM-DD-commit` build ID takes precedence over Windows product/file version metadata; missing or ambiguous identities remain unknown. Saving a custom result records this native version and the UTC recording time in `CompatibilityTestVersions`, keyed alongside the existing authoritative status dictionary. Legacy status-only results keep an unknown tested version until explicitly updated. Reset removes both status and version metadata; save failure rolls both back. Changing the executable never changes a saved result's version.

OrbitX checks the official KytyPS5 latest release at startup. For the managed installation it can update, patch, build to a staging directory and replace the installed package while preserving a rollback copy through hash verification. Unsafe source checkout state, an active Kyty process, or any failed build/verification prevents runtime replacement; game launches remain disabled while this update runs. See [the controller-menu patch workflow](../integrations/kytyps5/README.md).

Library cards and the editor reuse the main-page badge component for **Your result**, **Website** overall, and each website report. Version text distinguishes a known current-version test, a different version, and an unverified version. A version-only website report cannot establish a match to a local commit-specific build. Not tested never counts as a current-version test. Browse thumbnail badges mark custom results with **You**; their tooltip includes the recorded version, comparison and separate website status. UI review: comparison labels and version text accompany the shared badge colours; the existing labelled selector and keyboard/focus behaviour remain unchanged.

## Saved launch logs

Play captures standard output and standard error concurrently on background readers while OrbitX is running, with no separate console window. Each launch creates a UTF-8 file under the settings directory's `launch-logs` folder. The header records the start time, executable, detected build and launch arguments; the footer records the exit time and decimal/hex exit code. Output is flushed continuously, including partial lines. This records bytes KytyPS5 emits to its standard streams; it cannot recover output still buffered inside an abruptly terminated emulator or output configured exclusively to a separate file.

The library record persists only a generated log ID before the process starts. **View log** appears once that log exists and remains available after a crash or OrbitX restart. Orbit displays the latest launch in a selectable, scrollable text dialog with Refresh and Close; Classic provides the same saved content through its View log button. `POST windows/log` accepts only the retained library ID, rejects caller-supplied paths, and reads at most the last 2 MiB for the viewer. Complete per-launch files remain on disk and are never uploaded. New launches create separate logs; older files are retained. Log text is rendered as text, and Escape restores focus to the opener.

UI review: primary Play and destructive Delete retain distinct colours, text and visible focus rings; Delete has a progress dial and a visible hold instruction. Secondary controls have an accessible disclosure label and support Tab/Escape. The compatibility selector has a persistent label, and its dialog restores focus. Synthetic WebView2 checks cover poster geometry, disclosure actions, launch routing, compatibility save/reset/rollback, rejected early/replayed confirmations, cancelled holds and a full hold through the existing deletion transaction with an isolated fixture recycler. Native real-game deletion is not used for validation.

## Browser boundary

`OrbitFrontendHost` has its own WebView2 profile under the native settings directory, separate from provider-download WebViews. Static bundle members and the bounded API are answered in-process at `https://orbit.ps5catalog.invalid`; no HTTP listener, background web server or public endpoint exists. The original API client is unchanged. [WebView2 folder mapping bypasses WebResourceRequested](https://learn.microsoft.com/en-us/microsoft-edge/webview2/how-to/webresourcerequested), so both local assets and same-origin API use the request handler instead of a virtual folder mapping.

The main document is pinned to `/index.html`. Navigation/frame navigation is blocked; user-initiated external web links require the approved native browser prompt and existing `NetworkPolicy`. Popups, external schemes, permissions, certificate errors and download offers cannot acquire native access. Remote resources are limited to HTTPS/loopback images. CSP excludes remote scripts/connections, frames, objects, workers, base changes and form submissions. No host objects are exposed.

Web messages require the exact trusted sender **and** current trusted document, schema version 1, bounded JSON, no duplicate/additional fields and an allowlisted command: `ready`, `error`, `fullscreen`, `exitFullscreen`, `toolbar` (F6), or `navigate` to Settings/Downloads/My Library/Classic Windows. Native Appearance/page notifications carry only fixed commands/pages. Privileged management goes through the bounded same-origin Windows API described above. Unknown API paths/methods fail closed; cross-origin requests are denied with no CORS access. Provider windows retain disabled web messages, separate profiles and no management API bridge.

`GET/POST windows/settings` is a presentation adapter to the existing model. It exposes an explicit settings-field allowlist and named picker/updater/source actions, with a 16 KiB request-body limit for this route. Other routes retain their existing limits. It accepts user-entered settings paths only in their named fields/source drafts; library/download actions still accept retained identities rather than caller-supplied paths. Source draft fields are validated before dispatch, source edit availability and updater eligibility are rechecked on the dispatcher, and native confirmations remain authoritative. Saved passwords are returned only as masked indexes, with no password bytes or protected IGDB secret in state. The existing IGDB credential endpoint is unchanged.

Initialization, process or rendering failure displays a native status and Classic Windows. The saved interface/appearance preference is retained; restart retries Orbit. Classic controls stay available even while initialization is pending.

## Existing owners

Orbit actions resolve exact native identities at action time and dispatch to the existing Classic handlers and owners below. Polling never changes the selected native record.

| Workflow | Existing C# entry point and guarantees |
|---|---|
| Direct admission | `MainViewModel.DownloadAsync`, `DownloadAdmission`, `OrbitDownloadPolicy`; exact selected release and A1/A2 ownership. |
| Browser/import | `BrowserDownloadWindow`, `BrowserDownloadManager.Accept` / `ImportAsync`; provider isolation and A3 native writer ownership until terminal callbacks. |
| Queue actions | `PauseSelectedDownloadAsync`, `ResumeSelectedDownloadAsync`, `CancelSelectedDownload`, `RestartAsync`, `DiscardSelectedDownloadAsync`, `ClearAllDownloadsAsync`; use existing durable HTTP checkpoints and cleanup admission rules. |
| Completion/history | `DownloadCompletion` and `SettingsStore`; existing A4/A5 verification, recovery and atomic registration. |
| Library | Native `Library`/`LibraryView`, `AddLocal`, `ReinspectAsync`, `PrepareLibraryDeletion` and `DeleteLibraryEntry`; preserve exact paths, shared/active ownership and explicit deletion confirmation. |
| ZIP/RAR | `ExtractAsync`, `ExtractSelectedDownloadAsync`, `CheckExtractedDownloadAsync`; verified complete files, safe paths/CRC, current extraction/movement ownership. |
| Install | `InstallImageAsync` with native `InstallationConfirmation`/`InstallationChoice`, `ImageInstallationCoordinator`, package readers and installation journal; existing verified publication, source-retention and cleanup gates. |
| Launch | `CanLaunchSelected` then `MainViewModel.Launch` / `KytyLauncher`; preserve explicit compatibility result and existing launch confirmation. |

The Windows management components provide controls for these existing functions. Live provider compatibility and game launch success remain separate acceptance questions.

Provider windows hide completely when minimised or when a download is accepted, returning to the main app without changing its current screen. Downloads lists waiting provider sessions, then offers **Check status** on the admitted download row to restore its original window. The hidden browser keeps its native transfer alive. Classic exposes the same session controls. Closing a provider window removes its restore control; live windows are not persisted across restart.

Browser admission saves the original provider page in `DownloadJob.Url`, the expected filename, and the selected Orbit release metadata. Retry first attempts a resumable native transfer. If that fails, it reopens the saved provider page through the same isolated browser and native download admission process; matching offers continue automatically. Saved Orbit selections are checked against their original admission identity, including after catalogue refresh or restart. A provider HTTP error or AkiraBox unavailable-link response returns to the exact store item (or its title search); **Choose another download** provides that route when a provider remains idle. Failed history is replaced only when a new download is admitted. Provider verification still requires the user, and signed transfer capabilities are never replayed through direct HTTP.

## Upgrade procedure

1. Check the official release's published archive SHA-256; record the exact release URL and digest. Extract only `SOURCES.json`, checksums/notices and its inner source archive into a task-owned temporary directory. Check the inner archive against `SOURCE-SHA256SUMS`.
2. Inspect the new source's browser/API/layout contracts before replacing the vendored subset. Whitelist regular frontend files only; reject traversal, links and special files. Preserve exact bytes. Do not vendor keys, feeds, backend sources or commercial artwork.
3. Update `provenance.json` and regenerate `upstream-files.json` from those verified members. Review package lockfile/licence changes and each adapter substitution/build anchor. No automatic compatibility fallback is provided.
4. Run `UI/verify-upstream.ps1`, `UI/build-frontend.ps1 -Restore`, the Core/Browser suites, frontend contracts and Debug/Release builds. Verify all four real layouts, details, filters, favourites, restart, native navigation, native writer ownership, fullscreen/modal/input handling and security rejection cases.
5. Capture WebView2 previews at 1920×1080, 1280×720 and normal desktop size; compare the appropriate browser/native references in the official appearance guide. Keep commercial artwork captures local and untracked. Remove source acquisition archives and temporary validation folders; commit source, adapter, tests and concise evidence only.

See [frontend validation](orbit-frontend-validation.md) for commands, results and limitations.
